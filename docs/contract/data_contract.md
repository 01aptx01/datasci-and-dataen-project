# ขั้นที่ 1: กำหนด Data Contract ก่อนดึงข้อมูล

> **Data Contract** คือข้อตกลงและพันธสัญญาระหว่างแหล่งข้อมูลกับระบบ downstream ว่า ข้อมูลที่นำเข้ามาต้องมีโครงสร้าง รูปแบบ คุณภาพ และเกณฑ์การตรวจสอบที่ชัดเจนก่อนนำไปประมวลผลต่อ

---

## 1. ข้อมูลพื้นฐานของระบบ (Ingestion Specification)

| หัวข้อ | ข้อกำหนด / รายละเอียด |
| :--- | :--- |
| **แหล่งข้อมูล (Source)** | Yahoo Finance ผ่านไลบรารี `yfinance` |
| **สินทรัพย์ (Assets)** | `SPY` (หุ้นสหรัฐฯ), `IEF` (พันธบัตรรัฐบาลสหรัฐฯ), `GLD` (ทองคำ) |
| **ความถี่ (Frequency)** | รายวัน (Daily) เฉพาะวันเปิดทำการซื้อขาย |
| **ช่วงข้อมูล (Time Range)** | **`2021-09-27` ถึง `2026-09-25`**<br>• กำหนดขอบเขตแบบรวมทั้งวันเริ่มต้นและสิ้นสุด (Inclusive: `[2021-09-27, 2026-09-25]`)<br>• *หมายเหตุสำหรับการดึงผ่าน yfinance: เนื่องจากพารามิเตอร์ `end` เป็น exclusive ให้กำหนด `end='2026-09-26'` เพื่อให้ครอบคลุมข้อมูลถึงวันที่ `2026-09-25`* |
| **ระดับหน่วยข้อมูล (Granularity)** | 1 แถว แทนราคาของ 1 สินทรัพย์ ณ 1 วันซื้อขาย |
| **คีย์หลัก (Primary Key)** | `(date, ticker)` เพื่อรับประกันความไม่ซ้ำซ้อน |

---

## 2. ข้อกำหนดทางเทคนิคและการคำนวณ (Technical & Transformation Contract)

| หัวข้อ | ข้อกำหนด / รายละเอียด |
| :--- | :--- |
| **การปรับราคา (Price Adjustment)** | เลือกใช้ **`auto_adjust=True`** เพียงวิธีเดียวสำหรับทุก ticker เพื่อปรับราคาตาม Corporate Actions (ปันผล, แตกพาร์) โดยอัตโนมัติ<br>• **ชื่อคอลัมน์ราคาที่จะส่งต่อ**: กำหนดให้ใช้ชื่อคอลัมน์ **`close`** (ราคาปิดที่ปรับแล้ว) ส่งต่อให้ขั้นตอนคำนวณผลตอบแทนอย่างเป็นทางการ |
| **นิยามผลตอบแทนหลัก (Primary Return Definition)** | กำหนดให้ใช้ **Log Return (ผลตอบแทนลอการิทึม)** เป็นสูตรหลักของ Pipeline อย่างเป็นทางการ:<br>$$r_t = \ln\left(\frac{P_t}{P_{t-1}}\right) = \ln(P_t) - \ln(P_{t-1})$$<br>• **ชื่อคอลัมน์ผลลัพธ์**: `log_return`<br>• *(สูตร Simple Return จัดไว้เป็นทางเลือกสำหรับการทดลองในขั้นตอน Model Experimentation ในภายหลัง)* |
| **ปฏิทินซื้อขาย (Trading Calendar)** | อิงตามปฏิทินวันทำการของตลาดหุ้นสหรัฐฯ (NYSE/NASDAQ Calendar) เพื่อสร้างตาราง **วันที่คาดว่าจะมีการซื้อขาย (Expected Trading Days)** ไว้ใช้เป็นเกณฑ์เปรียบเทียบ |
| **เวลาของข้อมูล (Timezone & Availability)** | • กำหนด Timezone อ้างอิง เช่น `US/Eastern` หรือจัดเก็บในรูป `UTC`<br>• กำหนดเวลาที่ถือว่าข้อมูลพร้อมใช้งาน (Data Cut-off): **หลังตลาดปิดและกระบวนการ Ingestion ยืนยันว่าดึงข้อมูลเสร็จสมบูรณ์** |

## 3. เกณฑ์การตรวจสอบคุณภาพข้อมูล (Data Validation Rules)

ระบบต้องรันการตรวจสอบ Data Validation ต่อไปนี้ก่อนบันทึกหรือส่งต่อให้โมเดล:

1. **ความถูกต้องของ Schema และค่า**:
   - `date` ต้องอยู่ในรูปแบบวันที่มาตรฐาน (`YYYY-MM-DD`) และเรียงลำดับจากอดีตไปปัจจุบัน (Monotonic Increasing)
   - `ticker` ต้องเป็นหนึ่งในเซ็ตที่กำหนดเท่านั้น (`{'SPY', 'IEF', 'GLD'}`)
   - ราคาในคอลัมน์ `close` ต้องเป็นตัวเลข (Float) และมีค่ามากกว่า 0 เสมอ ($close > 0$)
2. **ความไม่ซ้ำซ้อน (Uniqueness)**:
   - ห้ามมี Composite Key `(date, ticker)` ซ้ำกันในชุดข้อมูล
3. **การตรวจจับความผิดปกติ (Anomaly Detection - Warning Flag)**:
   - กำหนดเกณฑ์เตือนเมื่ออัตราการเปลี่ยนแปลงของราคาใน 1 วันเกิน $\pm 20\%$ ($|r_t| > \ln(1.20) \approx 0.1823$ หรือ Simple Return เกิน $\pm 20\%$)
   - **แนวทางปฏิบัติ**: **ไม่ตัดแถวข้อมูลทิ้งหรือหยุด Pipeline อัตโนมัติทันที** เนื่องจากอาจเป็นความผันผวนจริงของตลาด (Extreme Market Event) ให้บันทึกเป็น Anomaly Flag ใน Audit Log และนำเข้าสู่กระบวนการ Quarantine เพื่อตรวจสอบยืนยันกับแหล่งข้อมูลต้นทางก่อนตัดสินใจ

## 4. นโยบายการจัดการข้อมูลขาดหายและข้อผิดพลาด (Missing Data & Failure Policy)

| สถานการณ์ | แนวทางปฏิบัติ |
| :--- | :--- |
| **การตรวจสอบข้อมูลขาดหาย (Missing Data Check)** | • **ตรวจสอบเทียบกับปฏิทินวันทำการจริง (Expected Trading Days)**: วันหยุดตลาดที่ทุกสินทรัพย์ไม่มีข้อมูลถือเป็นปกติ ไม่นับเป็นข้อมูลขาดหาย<br>• แจ้ง Warning/Error เฉพาะกรณีที่ Ticker ใดตัวหนึ่งขาดข้อมูลใน**วันที่คาดว่าตลาดเปิดทำการจริง**<br>• **ไม่อนุญาตให้ใช้ Forward-fill หรือ Interpolation ข้ามวันโดยพลการ** เว้นแต่จะมี business logic หรือเหตุผลรองรับที่บันทึกไว้ในสเปก |
| **เมื่อไม่ผ่านเงื่อนไข (Validation Failure)** | • ทำการบันทึก Log ระบุสาเหตุที่ผิดพลาด (Error Reason, Corrupted Rows, Ticker, Date)<br>• สั่งหยุดขั้นตอน (Fail-fast) หรือแยกข้อมูลที่มีปัญหาเข้า Quarantine สำหรับขั้นตอนที่ต้องใช้ข้อมูลนั้น เพื่อป้องกันไม่ให้ข้อมูลที่ผิดพลาดรั่วไหลไปยังโมเดล downstream |
