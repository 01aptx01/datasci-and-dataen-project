# ขั้นที่ 1: กำหนด Data Contract ก่อนดึงข้อมูล

> **Data Contract** คือข้อตกลงและพันธสัญญาระหว่างแหล่งข้อมูลกับระบบ downstream ว่า ข้อมูลที่นำเข้ามาต้องมีโครงสร้าง รูปแบบ คุณภาพ และเกณฑ์การตรวจสอบที่ชัดเจนก่อนนำไปประมวลผลต่อ

---

## 1. ข้อมูลพื้นฐานของระบบ (Ingestion Specification)

| หัวข้อ | ข้อกำหนด / ข้อเสนอ |
| :--- | :--- |
| **แหล่งข้อมูล (Source)** | Yahoo Finance ผ่านไลบรารี `yfinance` |
| **สินทรัพย์ (Assets)** | `SPY` (หุ้นสหรัฐฯ), `IEF` (พันธบัตรรัฐบาลสหรัฐฯ), `GLD` (ทองคำ) |
| **ความถี่ (Frequency)** | รายวัน (Daily) เฉพาะวันเปิดทำการซื้อขาย |
| **ช่วงข้อมูล (Time Range)** | ย้อนหลังประมาณ 5 ปี โดยระบุวันที่เริ่มต้น (`start_date`) และสิ้นสุด (`end_date`) ให้ชัดเจน (เช่น `2019-01-01` ถึง `2023-12-31`) |
| **ระดับหน่วยข้อมูล (Granularity)** | 1 แถว แทนราคาของ 1 สินทรัพย์ ณ 1 วันซื้อขาย |
| **คีย์หลัก (Primary Key)** | `(date, ticker)` เพื่อรับประกันความไม่ซ้ำซ้อน |

---

## 2. ข้อกำหนดทางเทคนิคและการคำนวณ (Technical & Transformation Contract)

| หัวข้อ | ข้อกำหนด / รายละเอียด |
| :--- | :--- |
| **ประเภทราคา (Price Type)** | ใช้ราคาที่ปรับผลกระทบจาก Corporate Actions แล้ว (เช่น เงินปันผล, แตกพาร์) โดยดึงเป็น **`Adjusted Close`** หรือใช้พารามิเตอร์ `auto_adjust=True` และบังคับใช้รูปแบบเดียวกันกับทุก ticker |
| **นิยามผลตอบแทน (Return Definition)** | กำหนดสูตรคำนวณผลตอบแทนให้สอดคล้องกันทั้ง 3 สินทรัพย์:<br>• **Simple Return**: $R_t = \frac{P_t}{P_{t-1}} - 1$<br>*(หรือ Log Return: $r_t = \ln(P_t / P_{t-1})$ ตามที่ตกลงในโมเดล)* |
| **ปฏิทินซื้อขาย (Trading Calendar)** | อิงตามปฏิทินวันทำการของตลาดหุ้นสหรัฐฯ (NYSE/NASDAQ Calendar)<br>• กรณีที่ ETF บางตัวขาดข้อมูลในวันเปิดตลาด: ต้องมีกลไกตรวจสอบ cross-check ทั้ง 3 สินทรัพย์ |
| **เวลาของข้อมูล (Timezone & Availability)** | • กำหนด Timezone อ้างอิง เช่น `US/Eastern` หรือแปลงเป็น `UTC`<br>• กำหนดเวลาที่ถือว่าข้อมูลพร้อมใช้งาน (Data Cut-off): **หลังตลาดปิดและกระบวนการ Ingestion ยืนยันว่าดึงข้อมูลเสร็จสมบูรณ์** |

## 3. เกณฑ์การตรวจสอบคุณภาพข้อมูล (Data Validation Rules)

ระบบต้องรันการตรวจสอบ Data Validation ต่อไปนี้ก่อนบันทึกหรือส่งต่อให้โมเดล:

1. **ความถูกต้องของ Schema และค่า**:
   - `date` ต้องอยู่ในรูปแบบวันที่มาตรฐาน (`YYYY-MM-DD`) และเรียงลำดับจากอดีตไปปัจจุบัน (Monotonic Increasing)
   - `ticker` ต้องเป็นหนึ่งในเซ็ตที่กำหนดเท่านั้น (`{'SPY', 'IEF', 'GLD'}`)
   - ราคาต้องเป็นตัวเลข (Float) และมีค่ามากกว่า 0 เสมอ ($Price > 0$)
2. **ความไม่ซ้ำซ้อน (Uniqueness)**:
   - ห้ามมี Composite Key `(date, ticker)` ซ้ำกันในชุดข้อมูล
3. **การตรวจจับความผิดปกติ (Outlier / Anomaly Detection)**:
   - ตรวจสอบอัตราผลตอบแทนที่กระโดดผิดปกติ (Return Spikes / Crashes) เช่น เปลี่ยนแปลงเกิน $\pm 20\%$ ในวันเดียว เพื่อป้องกัน Bad Data / Split Error

## 4. นโยบายการจัดการข้อมูลขาดหายและข้อผิดพลาด (Missing Data & Failure Policy)

| สถานการณ์ | แนวทางปฏิบัติ |
| :--- | :--- |
| **ข้อมูลขาดหาย (Missing Date / Price)** | • หากพบวันทำการที่ราคาขาดหาย (Missing Value) ให้บันทึก Warning/Error และ**ระงับกระบวนการคำนวณทันที**<br>• **ไม่อนุญาตให้ใช้ Forward-fill หรือ Interpolation ข้ามวันโดยพลการ** เว้นแต่จะมี business logic หรือเหตุผลรองรับที่บันทึกไว้ในสเปก |
| **เมื่อไม่ผ่านเงื่อนไข (Validation Failure)** | • ทำการบันทึก Log ระบุสาเหตุที่ผิดพลาด (Error Reason, Corrupted Rows, Ticker, Date)<br>• สั่งหยุดขั้นตอน (Pipeline Termination/Fail-fast) สำหรับกระบวนการที่ต้องนำข้อมูลชุดนี้ไปใช้งานต่อ เพื่อป้องกันข้อผิดพลาดลุกลามไปยัง downstream tasks |
